# Poolside it for me Extension Plan

## Goal

Build a Chrome / Chromium extension that lets a user open a side-panel chat and ask an agent to operate the current browser tab or nearby tabs.

Initial example:

- [ ] User opens Gmail or another mail web app.
- [ ] User opens the extension side panel.
- [ ] User writes: "Send my manager an email saying I am sick and will miss the meeting."
- [ ] Agent observes the page, navigates the UI, drafts the email, and asks for confirmation before sending.
- [ ] User confirms the final irreversible action.
- [ ] Agent sends or completes the task.

## Core product constraints

- [ ] Must work as a Chrome Manifest V3 extension.
- [ ] Must support Chromium-based browsers where possible.
- [ ] Must start with OpenAI / ChatGPT-compatible inference.
- [ ] Must not require a separate local backend for the first MVP.
- [ ] Must support user-provided API keys.
- [ ] Must keep the browser-control layer deterministic and auditable.
- [ ] Must not execute arbitrary JavaScript generated by the model.
- [ ] Must require human confirmation for irreversible or sensitive actions.
- [ ] Must be designed so Anthropic or other model providers can be added later.

## Current decisions

- [x] First prototype targets simple pages before Gmail or other complex apps.
- [x] First usable audience is developer / power-user.
- [x] Long-term direction should remain compatible with Chrome Web Store publishing.
- [x] MVP uses BYOK: the user enters their own OpenAI API key.
- [x] MVP works only with the active tab after user interaction.
- [x] Side panel can be opened on different sites, but agent state is scoped to the active tab/task first.
- [x] First agent implementation uses a custom loop with OpenAI Responses API.
- [x] OpenAI Agents SDK is not used in the first MVP.
- [x] MVP avoids a separate backend or local companion process.
- [x] Task history is stored locally for the MVP.
- [x] Side panel includes a debug view.
- [x] Debug logs must be easy to copy/export for analysis by humans or other agents.
- [x] First test target is a local playground HTML page with simple navigation and forms.
- [x] Confirmation policy starts with explicit modes instead of hidden heuristics only.

## Extension-only inference architecture

The first MVP should call OpenAI directly from the extension service worker or another extension page, not from a separate backend.

- [ ] Add `storage` permission for locally storing user settings and API key.
- [ ] Add `host_permissions` for `https://api.openai.com/*`.
- [ ] Store the user's OpenAI key in `chrome.storage.local`.
- [ ] Store task history in `chrome.storage.local`.
- [ ] Store debug traces in `chrome.storage.local`, with a size cap.
- [ ] Never expose the API key to content scripts.
- [ ] Never inject the API key into the web page.
- [ ] Route model requests through the extension service worker.
- [ ] Use direct `fetch()` to the OpenAI Responses API for the MVP.
- [ ] Avoid bundling a browser-side OpenAI SDK unless there is a clear benefit.
- [ ] If using the OpenAI JS SDK in an extension context later, explicitly review its browser credential warnings.
- [ ] Treat BYOK as acceptable for a developer MVP because the user's own local extension stores the user's own key.
- [ ] Revisit hosted backend only if we need centralized billing, key isolation, team accounts, analytics, abuse controls, or provider-side secrets.

Initial manifest shape:

```json
{
  "manifest_version": 3,
  "name": "Poolside it for me",
  "version": "0.1.0",
  "permissions": [
    "activeTab",
    "scripting",
    "sidePanel",
    "storage"
  ],
  "host_permissions": [
    "https://api.openai.com/*"
  ],
  "background": {
    "service_worker": "service-worker.js",
    "type": "module"
  },
  "side_panel": {
    "default_path": "sidepanel.html"
  }
}
```

## How the model sees the website

The model should not receive the raw full HTML page by default. The extension should convert the current tab into a compact, structured page snapshot.

### MVP approach: DOM and accessibility-style snapshot

- [ ] Inject a content script into the active tab after user invocation.
- [ ] Read visible text nodes from the page.
- [ ] Read visible interactive elements: buttons, links, inputs, textareas, selects, contenteditable regions, ARIA widgets, and likely clickable elements.
- [ ] Assign each actionable element a temporary stable ID, for example `el_1`, `el_2`, `el_3`.
- [ ] Extract semantic fields for each element: role, label, visible text, placeholder, input value, enabled/disabled state, checked/selected state, bounding box, and approximate DOM path.
- [ ] Return only the relevant viewport subset first.
- [ ] Add pagination/scroll observation if the page is too large.
- [ ] Send the structured snapshot to the agent as text/JSON.

Example shape:

```json
{
  "url": "https://mail.google.com/...",
  "title": "Inbox - Gmail",
  "viewport": { "width": 1440, "height": 900, "scrollY": 0 },
  "pageText": [
    "Inbox",
    "Compose",
    "Search mail"
  ],
  "elements": [
    {
      "id": "el_1",
      "role": "button",
      "name": "Compose",
      "text": "Compose",
      "visible": true,
      "enabled": true,
      "bbox": { "x": 24, "y": 96, "width": 120, "height": 48 }
    },
    {
      "id": "el_2",
      "role": "textbox",
      "name": "Search mail",
      "placeholder": "Search mail",
      "visible": true,
      "enabled": true,
      "bbox": { "x": 280, "y": 16, "width": 640, "height": 44 }
    }
  ]
}
```

The model then chooses actions against these IDs, not arbitrary selectors.

Example model action:

```json
{
  "tool": "click_element",
  "args": { "elementId": "el_1" }
}
```

The extension resolves `el_1` back to the DOM element and clicks it.

### Why not raw HTML first

- [ ] Raw HTML is too large and noisy for LLM context.
- [ ] Dynamic apps like Gmail have huge DOM trees with unstable class names.
- [ ] Full HTML increases privacy exposure.
- [ ] The agent does not need most markup; it needs task-relevant visible text and actions.

### Why not screenshot-first first

- [ ] Screenshots require vision-capable models or computer-use models.
- [ ] Coordinates are less stable than semantic element IDs.
- [ ] Screenshots are often more expensive and harder to debug.
- [ ] For text-heavy web apps, DOM snapshots are usually enough.

### Future hybrid approach

- [ ] Use DOM snapshot as the default observation channel.
- [ ] Use screenshot observation when DOM extraction is ambiguous.
- [ ] Use screenshot before risky final actions for user-visible confirmation.
- [ ] Add OCR/vision fallback for canvas-heavy or visually complex apps.
- [ ] Optionally support OpenAI Computer Use or Anthropic Computer Use in a separate advanced mode.

## Browser-control tools exposed to the agent

The model should only be able to call a small set of typed tools.

### Observation tools

- [ ] `observe_page`: return current structured page snapshot.
- [ ] `observe_element`: return more context around one element.
- [ ] `get_current_tab`: return active tab URL/title/status.
- [ ] `list_tabs`: return safe tab list with titles and URLs, subject to permissions.
- [ ] `capture_visible_screenshot`: optional fallback for visual checks.

### Action tools

- [ ] `click_element(elementId)`.
- [ ] `fill_element(elementId, text)`.
- [ ] `clear_element(elementId)`.
- [ ] `press_key(key)`.
- [ ] `scroll(direction, amount)`.
- [ ] `navigate(url)`.
- [ ] `go_back()`.
- [ ] `go_forward()`.
- [ ] `switch_tab(tabId)`.
- [ ] `open_tab(url)`.

### Safety tools

- [ ] `ask_user(question, choices)` for ambiguity.
- [ ] `request_confirmation(summary, risk, plannedAction)` before sending, deleting, purchasing, submitting forms, sharing sensitive data, or changing account settings.
- [ ] `finish(summary)` when the task is done.
- [ ] `abort(reason)` when the task is unsafe or impossible.

## Confirmation policy

The MVP should make confirmation behavior explicit and user-controlled.

### Mode 1: Confirm every action

Recommended default for early development.

- [ ] Before every browser action, show the action summary to the user.
- [ ] Include the selected element, target text, and reason.
- [ ] Require user approval before execution.
- [ ] Allow the user to reject and send feedback to the agent.
- [ ] Use this mode for debugging and trust-building.

### Mode 2: Allow all actions

Useful for local playground and fast iteration.

- [ ] Execute model-selected actions without per-step confirmation.
- [ ] Still keep an emergency stop button visible.
- [ ] Still enforce hard safety blocks for unknown unsupported tools.
- [ ] Log every action before and after execution.
- [ ] Do not use this as the default on sensitive real sites.

### Mode 3: Smart confirmation

Future mode after the basic loop works.

- [ ] Ask the model to classify each action as `safe_navigation`, `data_entry`, `external_submit`, `destructive`, `financial`, `auth_sensitive`, or `unknown`.
- [ ] Confirm only risky classes.
- [ ] Keep a deterministic policy override: destructive, financial, auth-sensitive, external submit, file upload, and send/post actions always require confirmation.
- [ ] Treat model safety classification as advisory, not authoritative.
- [ ] Log the model's risk classification and the deterministic policy decision separately.

## Agent options

### Option A: custom JavaScript/TypeScript agent loop

Recommended for MVP.

- [x] Use a custom TypeScript loop for the first MVP.
- [ ] Use the extension service worker for OpenAI API calls.
- [ ] Keep the side panel as UI and the content script as browser tool executor.
- [ ] Implement the loop ourselves: observe, ask model, validate tool call, execute, observe again.
- [ ] Use JSON schema / structured outputs for action selection.
- [ ] Keep all tool definitions in our codebase.
- [ ] Add provider abstraction so OpenAI can be replaced with Anthropic later.

Pros:

- [ ] Maximum control.
- [ ] Easier to enforce safety rules.
- [ ] Easier to debug.
- [ ] No dependency on a large agent framework.
- [ ] Best fit for Chrome extension restrictions.

Cons:

- [ ] We must implement loop state, retries, traces, and guardrails ourselves.
- [ ] Less out-of-the-box agent tooling.

### Option B: OpenAI Agents SDK for TypeScript

Good second step if we want more agent framework support.

- [ ] Define browser tools as SDK tools.
- [ ] Use a TypeScript backend runtime.
- [ ] Use sessions/tracing/human-in-the-loop patterns from the SDK.
- [ ] Keep actual browser actions inside extension-controlled tools.

Pros:

- [ ] Production-oriented agent primitives.
- [ ] Built-in tracing and handoff patterns.
- [ ] Good TypeScript fit.

Cons:

- [ ] Still needs our browser observation/action layer.
- [ ] May add abstraction before the MVP needs it.

### Option C: OpenAI Responses API with function calling

Good low-level API path.

- [x] Use this for the first agent implementation.
- [ ] Define browser tools as function tools or strict structured actions.
- [ ] Run a manual loop in the extension service worker.
- [ ] Store conversation and tool history ourselves.
- [ ] Use structured outputs for strict action schemas.

Pros:

- [ ] Simple and explicit.
- [ ] Less framework lock-in.
- [ ] Easy to port to another provider.

Cons:

- [ ] We build more orchestration ourselves.

### Option D: Stagehand / Browserbase-style automation

Useful for backend or local companion mode, not pure extension MVP.

- [ ] Use Stagehand when controlling a Playwright/Chromium browser outside the extension.
- [ ] Consider it for cloud-browser workflows.
- [ ] Do not depend on it for direct control of the user current Chrome profile in the first MVP.

Pros:

- [ ] Mature browser-agent primitives: observe, act, extract, agent.
- [ ] Better for automated browser sessions.

Cons:

- [ ] Not naturally inside a Manifest V3 extension.
- [ ] Harder to operate the user's already-open current tab without a companion process.

### Option E: browser-use / dev-browser

Useful references and possible future companion integrations.

- [ ] Study browser-use for agent design and browser task patterns.
- [ ] Study dev-browser for browser control API ideas.
- [ ] Avoid making either one a hard dependency in the pure extension MVP.

Pros:

- [ ] Existing agentic browser automation patterns.
- [ ] Good inspiration for action loops and benchmarks.

Cons:

- [ ] Usually assumes Python/Node/Playwright/runtime outside Chrome extension.
- [ ] Not a direct drop-in for MV3 extension architecture.

### Option F: OpenAI / Anthropic computer-use models

Advanced optional mode.

- [ ] Use when DOM-based control is insufficient.
- [ ] Provide screenshots and execute model-requested mouse/keyboard actions.
- [ ] Keep allowlists, confirmations, and sensitive-domain guardrails.

Pros:

- [ ] Can handle visual UI that DOM extraction misses.
- [ ] Closer to human-like screen control.

Cons:

- [ ] More expensive.
- [ ] Less deterministic.
- [ ] Higher safety risk.
- [ ] Requires careful human-in-the-loop design.

## Recommended MVP architecture

```text
Chrome side panel
  -> extension service worker
  -> content script in active tab
  -> OpenAI Responses API via direct extension fetch
  -> typed browser tool call
  -> extension validates action
  -> content script executes action
  -> observe again
```

## Side panel UX

- [ ] Chat tab: user task input, assistant messages, current run status.
- [ ] Settings tab: API key entry, model choice, confirmation mode.
- [ ] Debug tab: latest page snapshot, current tool call, action trace, raw model response.
- [ ] History tab: local task history with status, site, timestamp, and summary.
- [ ] Stop button: visible during every running task.
- [ ] Export logs button: copy/download JSON trace for the selected task.

## Debug trace format

Each task should create a structured trace that can be copied into a bug report or handed to another agent.

- [ ] Task id.
- [ ] Timestamp.
- [ ] Active tab URL and title.
- [ ] User instruction.
- [ ] Model provider and model.
- [ ] Confirmation mode.
- [ ] Step number.
- [ ] Observation summary.
- [ ] Full page snapshot or truncated snapshot reference.
- [ ] Model request metadata.
- [ ] Raw model response.
- [ ] Parsed tool call.
- [ ] Validation result.
- [ ] Confirmation decision.
- [ ] Execution result.
- [ ] Error details if any.
- [ ] Final status and summary.

Example:

```json
{
  "taskId": "task_2026_05_11_001",
  "status": "running",
  "instruction": "Fill the contact form with test data",
  "confirmationMode": "confirm_every_action",
  "steps": [
    {
      "step": 1,
      "type": "observe",
      "url": "chrome-extension://.../playground.html",
      "snapshot": { "elements": [] }
    },
    {
      "step": 2,
      "type": "model_action",
      "rawResponse": "...",
      "toolCall": {
        "tool": "fill_element",
        "args": { "elementId": "el_3", "text": "Alice" }
      },
      "validation": "ok",
      "confirmation": "approved",
      "execution": "ok"
    }
  ]
}
```
